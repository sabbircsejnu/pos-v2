# Mobile Backend API Coverage Matrix

**Audit date:** 2026-10-15  
**Scope:** Flutter M1-M9 screens and actionable capabilities in SRS/LLD v1.4, compared with current backend controllers, CQRS, persistence, authorization and tests.  
**Decision basis:** Single-Business / Multi-Outlet deployment; no B1-B4 Product ownership restructuring; VAT/refund/accounting reconciliation deferred; no unverified Net Sales KPI is approved. Mobile Catalogue, Inventory and Stock Take access is limited to BusinessOwner and SalesManager (mapped to authorized backend Manager/OutletManager roles); Salesperson and Cashier are denied these modules.  
**Result:** The backend is **not ready for full Flutter business-data integration**. The non-financial daily invoice activity endpoint, API-03 online catalogue reads, API-04 authorized Outlet inventory reads, API-05A online Stock Take sessions and the bounded API-05B count-operation sync protocol are implemented and tested below. Catalogue pinning, movement reconciliation and durable asynchronous submission remain unavailable. Existing route presence alone is not a readiness criterion.

## Status definitions

- **READY** — implemented for the stated contract, server-authorized, persistence semantics tested, typed contract documented.
- **PARTIAL** — useful existing behavior exists, but one or more contract, scope, persistence, security, or integration tests are missing.
- **MISSING** — no suitable backend route/implementation.
- **BLOCKED** — do not integrate pending a named business/security decision or authoritative data.
- **DEFERRED** — expressly outside the current release.

All routes labelled **proposed** are contract candidates from the LLD/backend plan, not existing routes. Generic ERP routes are not mobile-ready merely because they respond.

## Product Owner mobile module role contract (2026-10-15)

- Mobile Product Catalogue, Product/Variant Details, Barcode Lookup, Inventory and Stock Take are available only to the server-authenticated Business Owner and Sales Manager roles. Existing backend role names `Manager` and `OutletManager` are accepted as the authorized Sales Manager mapping; `SalesManager` is also recognized. No client-provided role value grants access.
- Mobile API handlers enforce both the allowed role and existing module permission(s); hiding navigation in Flutter is not an authorization control. Salesperson and Cashier access is denied in the mobile API scope only. Existing ERP/web POS permissions and workflows remain unchanged.
- Business Owner reads are bounded to the authorized Business Outlets returned by `IUserOutletAccessService`. Sales Manager reads are bounded to that user's assigned/authorized Outlets. Mobile Inventory endpoints accept an Outlet selector only when the server-side access service includes it.
- This is the Flutter navigation/route contract to be implemented by the separate mobile workstream; this backend task does not modify Flutter files.

## Completed first implementation slice

`GET /api/mobile/v1/insights/sales/activity`

This is deliberately a non-financial Sales Insights slice, chosen because higher-level financial trends are blocked by the deferred accounting decision while invoice recognition is testable from the existing sale status and timestamp.

### Contract for Flutter

Request:

```http
GET /api/mobile/v1/insights/sales/activity?startDate=2026-09-01T00:00:00Z&endDate=2026-09-03T23:59:59Z
Authorization: Bearer <ERP access token>
```

- `startDate` / `endDate` are optional UTC instants; defaults are `now - 30 days` and `now`.
- Inclusive time filtering uses `SaleDateTime` (legacy fallback `SaleDate`); daily buckets are UTC calendar dates.
- Reversed ranges return HTTP 400 with `message: "INVALID_DATE_RANGE"`. More than 366 UTC calendar days returns HTTP 400 with `message: "DATE_RANGE_TOO_LARGE"`.
- Response is zero-filled for each UTC day in the range (maximum 366 items). It does not accept Business, Outlet, user, role, or cashier IDs from the client.
- `invoiceCount` counts only `completed` and `refunded` sales, because a refunded sale remains an original completed-origin invoice. Voided, cancelled and other statuses are excluded.
- Owner/Manager require `reports.sales` and see server-authorized Outlet scope. SalesPerson requires `sales.view` and is filtered by authenticated real user ID. Cashier, unsupported roles, role-switched/global contexts are denied. The single-Business readiness guard is required before data access.
- Payload contains no sales amounts, net sales, average invoice value, customer, cost, profit or inventory fields. This endpoint is safe to integrate only for invoice-activity counts, not revenue or sales-value charts.
- Read-only endpoint: no offline mutation queue, idempotency key or pagination is needed. Date bounds are the query-size limit.

Sample response (one day with two eligible invoices):

```json
{
  "success": true,
  "message": "Operation successful",
  "data": {
    "startDateUtc": "2026-09-01T00:00:00Z",
    "endDateUtc": "2026-09-01T23:59:59Z",
    "timeZoneId": "UTC",
    "days": [
      { "date": "2026-09-01", "invoiceCount": 2 }
    ]
  }
}
```

No Daylight Saving or Asia/Dhaka local-day conversion is performed. The Flutter chart must label the series as UTC invoice activity and must not relabel it as Net Sales, revenue, demand or unit movement.

### Implementation, authorization and persistence

- Controller action and typed DTOs are in `MobileSalesDashboardController` / `MobileSalesDashboardDto.cs`; route is documented to OpenAPI via typed action response metadata.
- CQRS handler uses existing `ISalesReportReadScopeProvider`; infrastructure aggregation uses existing `Sale` persistence and returns only per-day counts. No migration or new persistence was added.
- Access reuses the mobile dashboard's server-derived role/permission logic and `IMobileSingleBusinessReadinessGuard`. The mobile report query has no client-supplied Outlet filter; database query filters by authorized Outlet IDs and, for salesperson, authenticated CashierId.
- Stable 400 error identifiers are `INVALID_DATE_RANGE` and `DATE_RANGE_TOO_LARGE`; response envelope follows the existing `ApiResponse<T>` convention. Cancellation token is passed to the query and EF aggregation.
