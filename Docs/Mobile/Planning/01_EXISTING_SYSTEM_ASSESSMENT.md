# Existing System Assessment

**Scope:** repository-code and checked-in-document discovery for the IraniMart Business mobile initiative.  
**Evidence date:** 2026-10-14.  
**Status vocabulary:** **VERIFIED** = directly observed in current repository/source; **PROPOSED** = recommendation, not present functionality; **UNKNOWN** = evidence is insufficient; **BLOCKED** = cannot be safely decided or implemented until an identified prerequisite is resolved.

> A source-code finding verifies what this checkout implements, not that a production deployment is configured or behaving identically. Existing worktree changes predate this planning work; no existing file was changed.

## Executive assessment

The ERP is a modular .NET/Angular application with reusable authentication, product/variant entities, stock-count workflow, stock-ledger/adjustment functionality, sales reporting, audit foundations, and durable integration-outbox infrastructure. The repository does **not** establish the mobile-specific catalogue revision/delta contract, durable offline count-operation protocol, mobile inbox, configurable notification policies, or forecasting capability required by SRS v1.4. The product identity and tenancy questions are material blockers: the inspected entities do not establish an authoritative Main Product Code mapped to uniquely barcoded variants under an agreed business scope.

The existing solution should remain the system of record. Extend the existing modular monolith and existing product/inventory/stock-count aggregates; do not create a second product or inventory master, and do not introduce a notification microservice without measured operational justification.

## Reuse guidance

1. **VERIFIED reuse:** existing auth/claims, business/outlet access services, product/variant entities and barcode lookups, stock-count lifecycle, stock adjustment/ledger, sale/report query handlers, audit infrastructure, durable outbox dispatcher, Angular routing, and existing test fixtures.
2. **PROPOSED extension:** versioned mobile read/command APIs in the existing API/Application layers; a catalogue projection over authoritative product/variant data; durable mobile count-operation receipts using the current stock-count/adjustment path; shared notification policy/inbox in the existing modular monolith.
3. **PROPOSED caution:** do not expose existing entity/EF shapes directly as mobile contracts. Add explicit DTOs, permission checks, scoped queries, and contract tests.
4. **BLOCKED:** catalogue business/outlet visibility, cross-table barcode collision remediation, mobile auth client flow, count-session concurrency/baseline rules, and outbox transaction integration require approved decisions before implementation. `ProductCode` is already the suitable Main Product Code field; adding another column is not recommended.
