### Barcode and legacy-data risk

`RetailPOSDbContext` configures separate unique indexes for Product.Barcode and ProductVariant.Barcode; it does not create one cross-table unique namespace. `ProductIdentifierLookupStore.BarcodeExistsAsync` checks variants, while product create/update paths check product barcodes separately. Consequently, a parent product barcode may collide with a variant barcode without the inspected index/precheck pair rejecting it. ProductCode is nullable for legacy compatibility, and database/data-quality state in production has not been queried.

**Required pre-export profile:** count null/blank ProductCode values; verify deployed indexes; detect duplicate raw and normalized barcodes across both tables; identify missing/orphan product/variant relationships; compare JSONB attributes against relational option selections; identify variants with no barcode or multiple business interpretations. Do not fabricate codes, auto-merge masters, or choose collision winners. Quarantine unresolved identifiers from scan resolution and route repair through authorized audited ERP procedures.

## 3. Proposed ADR resolutions

Each recommendation below remains **PROPOSED** until its named approvers record the decision. Accepted architectural direction is reflected as the default recommendation. “Blocking” refers only to the first dependent slice, not the entire mobile program.

### REC-AUTH-01 — ADR-AUTH-01: native authentication and token lifecycle

- **Current evidence:** `AuthController` exposes login, refresh-token, logout, logout-all and me flows. Login accepts credentials and RememberMe; access JWTs contain user/role/business/outlet/permission claims. `JwtTokenSettings` defaults to 60-minute access and 7-day refresh lifetime (deployment overrides were not verified). `RefreshTokenStore` hashes refresh tokens, rotates them transactionally, detects reuse/revocation and supports revocation. No native OAuth/OIDC/PKCE provider was verified.
- **Proposed decision:** For the initial native app, reuse the existing first-party login plus rotating refresh/logout endpoints only if Security explicitly approves this public-client pattern. The app is a public client: no client secret, embedded credential, or shared signing key. Store refresh token only in platform secure storage; keep access token memory-resident where feasible; send only over TLS. Prefer an external Authorization Code + PKCE/native broker only if an approved identity provider is available and contractually supported—do not invent one. Set access/refresh lifetimes, idle/max refresh lifetime, reuse response, MFA/step-up and revocation behavior as configurable server policy; candidate 15-minute access lifetime and current 7-day refresh ceiling are starting values for review, not facts or hardcoded app policy.
- **Reasoning/trade-offs:** Reuses tested rotation/revocation instead of introducing an unsupported OAuth flow; native password entry and long-lived public-client sessions need explicit risk acceptance. PKCE is preferable where an IdP supports it.
- **Security/data-integrity impact:** Threat model rooted devices, token theft/replay, device loss, clock skew, refresh race and revoked account; never log tokens; refresh single-flight and retry only according to server replay semantics; all writes reauthorize online.
- **Required automated tests:** secure-storage adapter; no secrets in binary/logs; access expiry; concurrent refresh; rotated-token replay/reuse revocation; logout/logout-all/device loss; MFA/locked/deactivated user; API authorization after token refresh/revocation; offline queue cannot submit with expired authorization.
- **Classification:** **BLOCKING for P2 auth implementation**; does not block non-auth Flutter architecture investigation.
- **Exact approval required:** Security/Identity owner approves native credential flow vs PKCE, token lifetime/rotation/reuse policy, MFA requirement, logout/device revocation and configurable policy authority; Architecture approves client/API contract.
- **Source references:** `src/RetailPOS.API/Controllers/AuthController.cs`; `src/RetailPOS.Infrastructure/Authentication/JwtAuthenticationTokenService.cs`; `JwtTokenSettings.cs`; `RefreshTokenStore.cs`; `src/RetailPOS.Domain/Entities/UserRefreshToken.cs`; `src/RetailPOS.API/appsettings.json` (defaults/configured values must be distinguished).

### REC-AUTH-02 — ADR-AUTH-02: business/outlet context and authorization

- **Current evidence:** JWTs may carry BusinessId/OutletId and role-switch claims. `TenantAccessService` provides business-scope checks; `UserOutletAccessService` delegates resolution/authorization to `IUserOutletAccess`. Existing security documentation identifies inconsistent endpoint coverage and no global tenant EF filter. Outlet.BusinessId is nullable.
- **Proposed decision:** Treat business/outlet IDs sent by the client as requests, never proof of access. After sign-in, fetch server-authorized contexts/outlets; allow selection only from that list. Revalidate scope on every API read/write (especially count create, sync, operation replay, submit and export); require explicit context-switch confirmation; partition local cache and pending operations by user/business/outlet and block switching while unresolved operations exist unless an approved recovery flow is completed. A mobile context must not use role-switch privilege as a substitute for actual user identity.
- **Reasoning/trade-offs:** Reuses existing access services while addressing endpoint-level gaps. Rechecking may add API work and requires explicit handling when grants change offline.
- **Security/data-integrity impact:** Fail closed for missing/ambiguous business/outlet. Revoked or changed grants stop writes and mark local work for authorized recovery; no client-controlled scope extension.
- **Required automated tests:** role/business/outlet allow-deny matrix; modified ID and cross-business/outlet attempts; null BusinessId outlet handling; context change with pending operations; grant revocation; cache partition and logout wipe/recovery; outlet assignment changes between sync and submit.
- **Classification:** **BLOCKING for P2 sign-in/context and P3 catalogue scope**; does not block unrelated report/forecast design.
- **Exact approval required:** Security and ERP/API owners approve effective-context contract, entitlement refresh, multi-outlet selection, context-switch/revocation behavior and Super Admin treatment.
- **Source references:** `TenantAccessService.cs`, `UserOutletAccessService.cs`, `ITenantAccessService.cs`, `IUserOutletAccessService.cs`, `RoleSwitchContext.cs`, `AuthController.cs`, `JwtAuthenticationTokenService.cs`, `Outlet.cs`, and current security isolation documentation.

### REC-CAT-01 — ADR-CAT-01: Product visibility and ownership scope

- **Current evidence:** Product/Category models do not carry direct business/outlet ownership fields; Outlet.BusinessId is nullable; Inventory is location-scoped. Generic product list/search paths do not establish a universal outlet filter. Intended master ownership policy cannot be inferred.
- **Proposed decision:** Preserve Product and Inventory ownership; add no ownership column or second master by assumption. Until a data owner establishes whether catalogue records are global, business-owned, or shared with explicit eligibility, mobile catalogue endpoints fail closed and return only products authorized by a documented server-side ownership/eligibility policy joined to the selected outlet/business. Inventory availability is not product ownership.
- **Reasoning/trade-offs:** Avoids leaking another business’s product data or introducing a breaking tenant schema. Requires an owner-approved source of eligibility before sync.
- **Security/data-integrity impact:** Scope checks are server-side on snapshots, deltas, barcode lookup, unknown resolution, images and session operations; test non-disclosure as well as denial.
- **Required automated tests:** global/shared/business/outlet fixture matrix once policy is selected; cross-business snapshot and delta denial; variant barcode lookup does not reveal out-of-scope existence; null outlet BusinessId denied unless explicit policy; stale grant behavior.
- **Classification:** **BLOCKING for P3 catalogue export and P5 operational use**, not for P2 auth shell.
- **Exact approval required:** Product master owner chooses ownership model and eligibility source; Security/tenant owner approves scope enforcement and null-owner behavior; DBA approves any later additive schema only if profiling proves necessary.
- **Source references:** Product/Category entities, Outlet.cs, Inventory.cs, `ProductReadStore.cs`, `ProductsController.cs`, tenant/outlet access services.

### REC-CAT-02 — ADR-CAT-02: barcode uniqueness and normalization

- **Current evidence:** Product.Barcode and ProductVariant.Barcode are independently indexed unique when present; no cross-table uniqueness is configured. Variant barcode is nullable. Product barcode lookup is not the confirmed VariantId resolver.
- **Proposed decision:** The stock-count scanner resolves only to exactly one authorized eligible ProductVariant barcode. A parent Product barcode is not an exact sellable variant and must return “not a variant barcode” unless an explicit product-level/manual selection flow is approved. Preserve raw scanner payload and leading zeroes. Use a versioned, symbology-aware canonicalization policy; initially do not case-fold, strip punctuation, or remove leading zeroes. Any canonical duplicate/cross-table collision is surfaced as ambiguous and quarantined; no arbitrary winner. New uniqueness enforcement/migration follows profiling and owner decision, not assumptions.
- **Reasoning/trade-offs:** Exact matching reduces false variant counts; it may require remediation for legacy formats and more explicit manual resolution.
- **Security/data-integrity impact:** Every lookup is scope-bound; unresolved barcode values are treated as potentially sensitive operational data and are not logged in clear telemetry.
- **Required automated tests:** cross-table collision; normalized collision; leading zeroes; each supported symbology/check digit; whitespace/control characters; case/punctuation-preserving behavior; duplicate variant barcode; parent code scan; out-of-scope barcode non-disclosure; no arbitrary selection.
- **Classification:** **BLOCKING for P3 scan catalogue and P5 count scanning**; data cleanup may be phased by approved severity thresholds.
- **Exact approval required:** Product and Inventory owners approve supported symbologies, canonicalization/versioning, handling of product-level codes, collision quarantine and remediation thresholds; Security approves lookup disclosure behavior.
- **Source references:** `RetailPOSDbContext.cs` Product/Variant indexes; `ProductIdentifierLookupStore.cs`; `ProductCreateStore.cs`; `ProductUpdateStore.cs`; `ProductReadStore.cs`; Product.cs and ProductVariant.cs.

### REC-CAT-03 — ADR-CAT-03: canonical attribute/value projection

- **Current evidence:** Named variations/options are relationally linked through Variation, VariationOption, ProductVariation, ProductVariationSelectedOption and ProductVariantOption. ProductVariant.Attributes is separately required JSONB. There is no inspected equality/completeness invariant.
- **Proposed decision:** Keep both ERP stores authoritative for their existing use; create one explicit read projection contract. Relational option selections supply stable IDs and configured display labels for named variations; JSONB supplies arbitrary attributes not represented by those selections. If the same normalized attribute key appears in both and values disagree, mark the variant projection invalid for mobile resolution/export until an authorized ERP correction; never choose one source silently. Pin the projected labels/values in each catalogue revision and stock session.
- **Reasoning/trade-offs:** Retains existing model semantics while supporting arbitrary attributes; mismatch quarantine is safer than silently hiding disagreement. A canonical repair policy may later migrate or standardize data.
- **Security/data-integrity impact:** Only attributes approved for the stock-count catalogue are exposed; no cost/private operational keys; pinned values support audit.
- **Required automated tests:** relational-only, JSON-only, matching overlap, conflicting overlap, duplicate option key, null/empty/malformed JSON, option removed/renamed between revisions, deterministic projection and pinned-session display.
- **Classification:** Projection contract is **BLOCKING for P3/P5**; choosing a future single authoritative storage representation can be safely deferred unless profiling proves repair is required.
- **Exact approval required:** Product master owner approves key naming, merge/display semantics and invalid-row remediation; Security approves attribute allowlist.
- **Source references:** entity and EF mapping files listed under REC-01; `ProductVariationsReadStore.cs`; `ProductCombinationsReadStore.cs`.

### REC-API-01 — ADR-API-01: versioned mobile API contract

- **Current evidence:** Most general ERP controllers use unversioned `/api/[controller]` routes; HR/payroll areas already use explicit `/api/hr/v1/...` or `/api/payroll/v1/...` prefixes. No general API versioning policy covering mobile compatibility was verified.
- **Proposed decision:** Introduce additive mobile routes under `/api/mobile/v1/`. Use explicit DTOs and stable error codes/problem details, UTC instants, business-zone date rules, bounded pagination, opaque revision/cursor tokens, correlation IDs and idempotency keys for commands. Add optional response fields compatibly; breaking changes require `/v2`, not semantic mutation of v1. Publish OpenAPI/contract fixtures and support at least the current and immediately previous released app versions; announce deprecation and allow an approved migration window before retiring a major version. Reuse existing auth routes only under their separately approved auth decision.
- **Reasoning/trade-offs:** A mobile version boundary contains compatibility risk without requiring versioning of every existing ERP endpoint. It adds contract maintenance.
- **Security/data-integrity impact:** Scope is derived and checked server-side regardless of route version. Reject oversized page/batch requests; do not expose internal exception text or sensitive existence data. Idempotency behavior is stable across retries.
- **Required automated tests:** OpenAPI generation/contract diff; backward-compatible additive change; v1 error schema; unsupported version; old-supported-client integration; paging/cursor tampering; correlation propagation; idempotent retry and unauthorized scope.
- **Classification:** **BLOCKING for P2 API client contract**; backend implementation can follow the approved contract and does not block architecture-only work.
- **Exact approval required:** API owner and Architecture approve route namespace, DTO/error conventions, compatibility window, deprecation notice, OpenAPI source of truth and client-support policy; Security approves error disclosure and scope policy.
- **Source references:** Existing API controller routes; versioned HR/payroll controllers and HTTP samples; `04_BACKEND_API_AND_DATABASE_PLAN.md`.

### REC-01 — Reuse ProductCode for Main Product Code and preserve ERP identity

- **Classification:** ProductCode mapping is **VERIFIED**; projecting and exporting are **BLOCKED** on ownership/scope approval and data-quality assessment.

### REC-02 — ADR-STK-01: blind baseline and movement-aware reconciliation

- **Current evidence:** ERP stock counts and stock adjustments/ledger remain server-side. Existing count entities do not provide a verified mobile baseline/lease/movement reconciliation protocol. POS sales and inventory movements must continue while a count is in progress.
- **Proposed decision:** Use a blind baseline captured by the server when the session opens; do not show expected stock to the counter and do not lock inventory. Keep baseline and movement evidence server-side. If an offline observation has uncertain capture time relative to movements, do not automatically calculate/post a variance: flag for reviewer evidence or recount.
- **Reasoning and trade-offs:** Preserves live POS operations and ERP authority while avoiding false arithmetic on an observation whose timing is not trustworthy. More cases may need review/recount; this is safer than silently adjusting.
- **Concurrency/reconciliation example:** Baseline 20; during the count there is a sale of 3 and receipt of 8, yielding current stock 25. An offline physical count of 22 whose capture time is unknown cannot safely imply a variance of -3 against baseline or -? against current stock. The system must show the movement sequence to an authorized reviewer and require a comparable-time decision or recount before adjustment.
- **Security/data-integrity impact:** Baseline is hidden from counters; movement evidence and reconciliation are permission-gated and audited; only ERP approval/posting may alter stock.
- **Required automated tests:** Movement before/after count comparison; uncertain observation time routes to conflict/recount; no automatic stock adjustment; blind-count DTO redaction; adjustment approval and at-most-once ledger posting; concurrent POS sale does not block or get lost.
- **Classification:** **BLOCKING** before server stock-count protocol and offline submission (P4/P5).
- **Exact approval required:** Inventory owner and Finance approve baseline timestamp, blind-count visibility, movement categorization, and reviewer/recount outcomes; Security approves visibility of movement details.
- **Source references:** `src/RetailPOS.Domain/Entities/StockCount.cs`, `StockCountLine.cs`, `Inventory.cs`; `src/RetailPOS.API/Controllers/StockCountsController.cs`; existing stock adjustment/ledger handlers and stock-count lifecycle/concurrency tests; SRS stock-count requirements.

### REC-03 — ADR-STK-02: single-device mobile lease, not inventory lock

- **Current evidence:** Existing server stock-count workflow does not establish a mobile device lease or safe merge contract. Existing audit/concurrency infrastructure can support an explicit server-side lease and conflict tests.
- **Proposed decision:** Permit one active mobile editing lease per count session. Lease duration and heartbeat/renewal interval MUST come from validated configuration (deployment/business policy), never hardcoded constants. Store the effective policy/version with each session; policy changes apply to newly acquired/renewed leases according to an approved rollout rule, while immediate server revocation remains possible. Require heartbeat interval < lease duration with a bounded safety margin. Candidate initial values for review only: 12-hour lease, 5-minute heartbeat. Offline evidence remains durable after expiry but cannot be submitted until user/device is reauthorized and the server reconciles. No silent takeover. An authorized supervisor may explicitly take over, with previous-device unacknowledged operations marked for conflict review. The lease applies only to mobile editors; POS sales and inventory transactions remain unlocked.
- **Reasoning and trade-offs:** A simple single-writer rule is easier to reason about than a multi-device merge, while offline work remains recoverable. Configurability permits operational tuning; policy versioning and validation are needed to prevent permanent leases or unintended simultaneous writers.
- **Concurrency/reconciliation example:** Device A owns session revision 7 and records 5 units for variant V offline. Lease expires. Supervisor authorizes Device B takeover at revision 8; B records 6 units for V. On reconnect A's old operation is retained but flagged stale; server must not sum 5+6 or apply last-write-wins. Reviewer selects/recounts a value after reviewing both operation histories and any stock movements.
- **Security/data-integrity impact:** Lease is bound to authenticated user, business/outlet, session and device registration; expiry/revocation checked server-side. Audit acquire/renew/expire/takeover and preserve original operation lineage.
- **Required automated tests:** lease exclusivity under concurrent requests; configuration loading/change/invalid-value rejection; heartbeat and lease boundaries/clock skew; renewal/idempotency; expiry offline reauthorization; explicit takeover; stale writer receipt; revoked user/device; POS inventory operations remain available; old/new operation conflict remains reviewable.
- **Classification:** **BLOCKING** before P4/P5.
- **Exact approval required:** Inventory owner approves single-device rule and takeover/recovery; Security approves device binding and revocation; Operations approves configuration owner/storage, permitted bounds, initial values, heartbeat constraint and change rollout. Initial durations are not final until approved.
- **Source references:** `StockCount.cs`, `StockCountLine.cs`, `StockCountsController.cs`, current stock-count permission/lifecycle code and PostgreSQL concurrency tests; SRS STK-009/STK-021.

### REC-04 — ADR-STK-03: explicit scope and full/partial completeness

- **Current evidence:** Existing count models associate records with locations and variants, but mobile session scope-completeness declarations and absent-item semantics are not established.
- **Proposed decision:** Pin a server-authorized outlet plus explicit category/SKU scope and catalogue revision at session creation. A partial-scope omission means “not counted/not in scope,” never zero. A declared full-scope omission becomes only a proposed zero line after operator explicitly marks the scope complete; authorized ERP reconciliation/reviewer disposition is still required before adjustment.
- **Reasoning and trade-offs:** Prevents a missing scan, incomplete offline session, or filtered subset from becoming a stock write-off. It adds an explicit completeness action and review burden.
- **Concurrency/reconciliation example:** Session scope includes variants A/B/C. A and B have observations; C has no operation. In a partial category subset, C is outside scope and is untouched. In a full-outlet session marked complete, C appears as “not observed/proposed zero” requiring reviewer reconciliation; it is not submitted as a confirmed zero count automatically.
- **Security/data-integrity impact:** Server pins the authorized scope and rejects client-added variant IDs. Completion is actor/time/audit attributed; counts cannot change outlet silently.
- **Required automated tests:** Tampered scope rejected; partial absence unchanged; explicit full-scope completion produces unresolved omission; incomplete uploads cannot mark scope complete; scope and revision remain pinned across resumes; reviewer approval required.
- **Classification:** **BLOCKING** before P4/P5 session protocol.
- **Exact approval required:** Inventory owner approves definitions of full and partial scope, completion evidence and omitted-item review; Security approves outlet authorization and context-switch behavior.
- **Source references:** `StockCount.cs`, `StockCountLine.cs`, `Inventory.cs`, stock-count session/create/submit handlers and permission tests; SRS STK-001/STK-012.

### REC-05 — ADR-STK-04: durable operations, idempotent submission and evidence retention

- **Current evidence:** Existing stock-count workflows have no verified client operation UUID/payload-hash receipt protocol, nor an agreed mobile audit retention duration.
- **Proposed decision:** Append immutable client operations with UUID, payload hash, session, pinned revision and actor/device provenance. Exact replay returns its original receipt; reuse of an ID with changed payload conflicts and is audited. Submission requires online authenticated scope, every operation acknowledged/resolved, matching expected session revision, and an idempotent submission receipt. Corrections after submission use authorized ERP reopen/recount, never overwrite prior evidence. Retain operations and receipts through finalization and for at least the approved audit/legal retention period; do not assume a number of years.
- **Reasoning and trade-offs:** Safe retries are essential after network timeouts. Durable receipts cost storage and require explicit purge rules but prevent duplicate count effects and preserve defensible reconciliation.
- **Concurrency/reconciliation example:** Client submits operation O7 with hash H1; the server commits but response times out. Retrying O7/H1 returns the same accepted receipt and has one effect. Retrying O7 with H2 returns conflict, emits audit evidence and does not alter the count. Repeating the session submit key returns the original submission receipt, not a second adjustment.
- **Security/data-integrity impact:** Enforce session/business/outlet authorization on every write and replay. Hash and actor/device evidence are integrity metadata, not substitutes for authorization. No client directly posts inventory.
- **Required automated tests:** Replay and altered-payload conflict; concurrent duplicate operation insert; transaction rollback; partial batch receipts; timeout recovery; submit replay; revision mismatch; correction/reopen lineage; retention purge boundary and no premature evidence deletion.
- **Classification:** **BLOCKING** before P4/P5; exact retention duration is **BLOCKING** before production launch but may be provisionally implemented with configurable policy after approval.
- **Exact approval required:** Inventory owner approves protocol/correction lifecycle; Audit/Compliance/Legal approve retention period and purge exceptions; DBA/Operations approve storage/index/backup behavior.
- **Source references:** `StockCount.cs`, `StockCountLine.cs`, audit entities/interceptors/services, stock-count lifecycle and adjustment-draft handlers, existing PostgreSQL concurrency and audit tests; SRS STK-013..020 and SYNC-003..006.
