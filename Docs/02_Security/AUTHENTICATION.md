# Authentication - Current Implementation (POS v2)

Updated: 2026-06-07

## Current implementation summary

- The API uses JWT Bearer authentication configured in `src/RetailPOS.API/Program.cs`.
- Access tokens are generated by `TokenService` (`src/RetailPOS.API/Services/TokenService.cs`) with user, role, business, outlet, and permission claims.
- Refresh tokens are generated as cryptographically strong random values and stored hashed in `UserRefreshTokens`.
- Passwords are hashed with BCrypt in `AuthService` and onboarding flows (`src/RetailPOS.API/Services/AuthService.cs`, `src/RetailPOS.API/Services/BusinessOnboardingService.cs`).
- Invitation-based first-password setup is implemented via `UserInvitations` and `AuthService.CompleteInvitationAsync`.
- Business owner role-switch authentication context is token-claim based (`RoleSwitchContext`, `RoleSwitchService`).
- Audit events are recorded for login, refresh success/failure, logout, and revoked refresh token reuse attempts.
- Auth endpoints have IP-based fixed-window rate limits (login/register/refresh).
- Frontend stores token, refresh token, and user profile in `localStorage` and attaches Bearer token via `auth.interceptor.ts`.

## Current flow explanation

1. User sends credentials to `POST /api/auth/login`.
2. `AuthService.LoginAsync` loads user + role + outlet, checks:
   - active user
   - BCrypt password hash
   - `MustResetPassword` gate
   - default outlet requirement for non-outlet-exempt roles
3. `TokenService.GenerateAccessToken` issues JWT with:
   - identity claims (`NameIdentifier`, `Email`, `userId`)
   - role claims (real role and effective role)
   - tenant claims (`businessId`, `outletId` when available)
   - permission claims from role JSON (`permission`)
4. Frontend persists token/user in `localStorage`; interceptor injects `Authorization: Bearer <token>`.
5. API validates JWT on subsequent requests.
6. For invitation completion (`POST /api/auth/complete-invitation`): token hash is checked, password set, `MustResetPassword=false`, token returned.
7. For owner role switch (`POST /api/auth/switch-role`): a new JWT is issued with acting role/outlet claims and a hashed refresh token is persisted.
8. For refresh (`POST /api/auth/refresh-token`):
  - access token signature/issuer/audience are validated (lifetime bypassed for refresh extraction)
  - user must exist and be active
  - refresh token hash must exist for user, must be non-revoked, and must be non-expired
  - token is rotated: current refresh token revoked, replacement hash stored, new refresh token issued
9. For logout (`POST /api/auth/logout`): all active refresh tokens for the user are revoked.
10. Login/register/refresh requests are rate-limited by source IP to reduce brute-force and token abuse.
11. Register endpoint is no longer public; it is restricted to Super Admin and assigns only constrained non-privileged default roles.

## Gaps or risks found

- Secrets are hard-coded in development config.
  - `src/RetailPOS.API/appsettings.json` contains plaintext DB password and JWT secret.
- Frontend token storage in `localStorage` increases XSS blast radius.
- Access token revocation/deny-list is still not implemented (logout revokes refresh tokens only).

## Recommended improvements

- Consider adding access token deny-list or very short access token TTL for faster post-logout/session-compromise containment.
- Move all credentials/secrets to environment variables or secure secret stores.
- Add account lockout policy on repeated failed login attempts (rate limits now reduce brute-force pressure but are not account-aware).
- Keep current localStorage token storage for compatibility now, but plan migration to an HttpOnly-cookie or BFF-backed session model.

## Acceptance criteria

- JWT validation rejects invalid issuer/audience/signature/expired tokens (already implemented).
- Non-outlet-exempt roles cannot authenticate without an assigned default outlet (already implemented).
- Invitation completion must set password and clear `MustResetPassword` before successful login (already implemented).
- Role-switch token must preserve real role identity and set acting role claims (already implemented).
- Refresh token endpoint must issue and validate persisted hashed refresh tokens with rotation and expiry checks (implemented).
- Logout must invalidate active refresh tokens and prevent new access token issuance from old sessions (implemented for refresh token path).
- Role-switch must reject acting outlet ids outside the current user business scope (implemented).
- Auth endpoints must enforce baseline request throttling (implemented).
